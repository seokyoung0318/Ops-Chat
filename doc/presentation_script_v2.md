## 슬라이드 4. 핵심 개선 ① RAG (60초)

먼저 매뉴얼 고르기입니다.
키워드 규칙을 bge-m3 임베딩 의미 검색으로 바꾸고, 유사도가 0.5 미만이면 억지로 고르지 않고 "매뉴얼을 찾지 못했다"고 표시하게 했습니다.

평가는 질문 23개에 정답을 붙이고, 답변 문장이 아니라 어떤 매뉴얼을 골랐는지로 채점했습니다. LLM 문장은 매번 달라지기 때문입니다.

(표 위에서 아래로)
기존 규칙은 57%였습니다.
질문만으로 검색하니 74%까지 올랐습니다.
그래서 알림 정보까지 넣으면 더 좋아질 거라 생각했는데, 오히려 61%로 떨어졌습니다.

(잠깐 쉬기)
원인을 보니, 시스템 이름이 없는 질문에서는 기본 조회 대상인 auth-service의 "latency" 알림이 검색어에 섞여서 엉뚱한 질문까지 전부 지연 매뉴얼로 끌려가고 있었습니다.

추가로 규칙이 구조적으로 못 고르던 새 매뉴얼은 5개 중 4개, 범위 밖 질문은 3개 모두 "매뉴얼 없음"으로 판별했고, 늘어난 시간은 질문당 약 37밀리초입니다.

## 슬라이드 5. 핵심 개선 ② 모르는 시스템 + 멀티 에이전트 (45초)

두 번째는 아까 billing-service 장면입니다.
이제 질문에서 시스템 이름을 뽑아 목록과 대조하고, 모르는 시스템이면 조사와 답변 작성은 건너뛰고(질문 분류용 작은 모델 호출 한 번만 남습니다) 바로 "조회할 수 없습니다"라고 안내합니다.
38초 걸려 틀린 답을 하던 것이 1.8초 안내로 바뀌었습니다.

다음은 멀티 에이전트입니다.
기존에는 상태를 조회한 뒤 매뉴얼을 고르려고 재조사를 한 번 더 돌았는데, 새 구조에서는 runbook 에이전트가 수치와 로그를 받자마자 검색합니다.
기본값은 기존 방식이고 PIPELINE=multi로 바꾸면 새 구조가 돌아서, 조사가 실행되는 21문항으로 두 방식을 비교했습니다.
(표나 숫자 가리키기)
정확도는 17개 대 17개로 같았고, 평균 조사 라운드는 1.86에서 1.00으로, 재계획은 0.86회에서 0회로 줄었습니다.
대신 로그 조회가 추가되어 MCP 호출이 질문당 1회 늘었습니다.
시간 차이는 수십 밀리초라 오차 범위여서 근거로 쓰지 않았습니다. 그래서 "정확도를 높였다"가 아니라 "정확도는 유지하면서 되돌아가는 반복을 없앴다"고 말씀드립니다.

> 시간이 모자라면: "멀티 에이전트로 정확도는 그대로 두고 재조사 반복을 없앴습니다. 대신 MCP 호출이 한 번 늘었습니다."까지만 읽는다.

## 슬라이드 8. 한계와 트레이드오프 (약 60초)

(슬라이드의 줄을 위에서 아래로 가리키며. 나머지는 발표자 노트에 있다)

한계 첫째, route가 장애가 아닌 질문도 장애로 분류합니다.
"사무실 프린터가 인쇄가 안 돼요"가 조사 경로를 탔는데, 유사도가 0.496으로 임계값 0.5 바로 아래라서 간신히 "매뉴얼 없음"으로 끝났습니다.

둘째, 임계값 0.5는 처음에 임의로 정한 값이었습니다.
그래서 0.30부터 0.74까지 전 구간을 다시 훑어봤고, 0.50에서 0.54 사이가 가장 좋았습니다. 지금 값은 그 안에 있습니다.
다만 같은 질문으로 고른 값이고 범위 밖 표본이 여섯 개뿐이라, 최적값이 아니라 유력한 구간이고 새 질문으로 재보정이 필요합니다.

트레이드오프는 세 가지입니다.
하나, 재조사는 최대 한 번, 재작성은 최대 세 번으로 막아 무한 루프는 없앴지만, 상한에 닿으면 불합격 답도 내보냅니다.
둘, RAG는 정확도를 올린 대신 1.2기가 모델과 질문당 수십 밀리초를 썼습니다.
셋, 의존성 주입 덕분에 코드를 바꾸지 않고 Ollama에서 OpenAI로 바꾸자 평균 49초가 5초가 됐지만, 과금이 생기고 질문이 외부 서버로 나갑니다. 빨라진 것은 우리 코드가 아니라 AI를 돌리는 곳이 바뀐 효과입니다.

추가 개선으로는 Hybrid 검색 비교, 새 질문 세트로 임계값 재보정, Human-in-the-loop 구현을 계획하고 있습니다.

> 시간이 모자라면: 한계 첫째와 트레이드오프 셋째만 읽고 "나머지는 슬라이드와 노트에 정리했습니다"로 넘긴다.

## 리허설 메모

- 시간 주의: 슬라이드 8을 늘렸더니 전체가 5분을 넘는다(약 5분 40초 예상). 아래 순서로 줄여 5분 안에 맞추고 반드시 소리 내어 한 번 재 본다
- 시간이 넘치면 자르는 순서: 슬라이드 6의 모듈화 문장 → 슬라이드 4의 "추가로" 문장 → 슬라이드 2의 코드 설명 문장 → 슬라이드 7을 숫자 두 개로 축소 → 슬라이드 8은 한계 첫째와 트레이드오프 셋째만
- 꼭 살릴 문장: 슬라이드 2 "틀렸다는 사실이 드러나지 않는다", 슬라이드 4 "오히려 61%로 떨어졌다", 마무리 문장
- 상세도(`structure_detail.png`)는 본 발표에 넣지 않고 질문이 나올 때 쓰는 백업 슬라이드로 둔다
- 예상 질문 대비
  - "왜 BM25나 하이브리드는 안 했나요?" → 시간 우선순위상 필수 요소를 먼저 했고, 남은 오답이 키워드 일치 문제인지 원인 분석 후 비교할 계획
  - "83%는 믿을 만한가요?" → 개발 세트라 과적합 위험이 있어 검증 20문항(85%)으로 따로 확인. 단 20문항이라 1문항이 5%p이고 같은 작성자가 두 세트를 만들었다는 한계가 있음
  - "0.5는 어떻게 정했나요?" → 처음엔 임의로 정한 값이었다. 그래서 0.30~0.74 전 구간을 43문항(개발 23 + 검증 20)으로 다시 훑었고(`eval/threshold_sweep.py`), 0.50~0.54가 최적 구간(36~37/43), 0.52가 최고(37/43)였다. 현재 0.50은 그 안에 있고 최고보다 1문항 적다. 단 같은 질문으로 고른 것이고 범위 밖 표본이 6개뿐이라 '최적값'이 아니라 '유력한 구간'이다. 0.52만 범위 밖 최고(0.509)와 정답 최저(0.528) 사이의 깨끗한 틈에 있지만, 같은 질문에 다시 맞추는 셈이라 새 질문 세트로 확인한 뒤에 바꾼다
  - "route 보정의 부작용은 없나요?" → 있다. 시스템 이름이 있으면 모델이 잡담이라 해도 장애로 바꾸기 때문에, 설명을 묻는 질문(예: "auth-service가 뭐하는 서비스야?")도 장애 경로로 간다(가짜 모델로 재현, 실제 모델로는 미측정). 틀린 사실을 말하는 것은 아니고 질문 의도와 다른 진단형 답변이 나오는 문제다. 장애를 잡담으로 놓치는 쪽이 더 위험하다고 보고 재현율을 택했다. 개선 방향은 '시스템 이름 + 증상 단어(느려, 에러 등)'가 함께 있을 때만 보정하는 것
  - "프린터 질문은 왜 장애로 분류됐나요?" → 시스템 이름이 없는 질문이라 보정 코드가 아니라 작은 모델 자체의 오분류다. 유사도가 0.496이라 임계값 0.5 바로 아래에서 "매뉴얼 없음"으로 걸러졌다. 임계값이 조금만 낮았으면 엉뚱한 매뉴얼이 붙었을 것이다
  - "Ollama에서 multi가 15초 빨랐던 건 구조 효과 아닌가요?" → 아니다. 장애 질문 8개를 1회씩 잰 값(single 57.1초, multi 41.7초)이고 질문별 편차가 크다(25~112초, 한 질문은 오히려 multi가 14초 느림). 구조가 바꾸는 부분은 1초 미만이다. 편차가 작은 OpenAI(5.2초 vs 4.4초)에서는 차이가 0.1~1.3초로 single의 시연용 지연(약 0.7초)과 거의 같다
  - "OpenAI로 바꾸면 되는데 왜 Ollama를 쓰나요?" → 비용과 데이터 때문이다. Ollama는 무료이고 질문이 내 컴퓨터를 떠나지 않는다. OpenAI는 약 10배 빠르지만(8개 질문, 1회씩이라 대략의 크기) 과금과 외부 전송이 따른다. 어느 쪽을 쓸지는 코드를 바꾸지 않고 환경변수로 고른다
  - "멀티 에이전트가 단일 에이전트보다 나은가요?" → 정확도는 17/21로 같다(두 방식이 다른 매뉴얼을 고른 질문은 0건). 좋아진 점은 재조사·재계획이 없어진 것(조사 라운드 1.86→1.00)이고, 대가는 MCP 호출 1회 증가. 시간은 55.9ms 대 49.8ms로 오차 범위라 "빨라졌다"고 말하지 않는다
  - "정확도가 같은데 왜 바꿨나요?" → 두 방식이 같은 검색 로직을 쓰니 정확도가 같은 것은 당연하다. 목적은 정확도가 아니라 되돌아가는 루프를 없애 구조를 단순하게 하고, 로그라는 정보 출처를 서브 에이전트로 분리하는 것
  - "빨라졌나요?" → 조사 단계만 재면 55.9ms 대 49.8ms로 차이가 없다. 답변까지 전부 돌린 OpenAI 10문항은 평균 4.67초 대 3.99초지만, single에 시연용 0.35초 지연이 재조사 라운드마다 들어 있어 그 차이(약 0.7초)와 거의 같다. 구조의 효과로 말하지 않는다
  - "루프가 무한히 돌 수 있지 않나요?" → 재조사는 최대 1회(replan_rounds), 검수 후 재작성은 최대 3회로 막아 두었다. 대신 3회 불합격해도 답을 내보내는 방식이라 검수는 형식(30자 이상, 번호 포함)만 본다는 한계가 있다
  - "로그 데이터는 진짜인가요?" → 가짜 샘플 데이터다(과제 범위상 실제 로그 수집은 하지 않음)
